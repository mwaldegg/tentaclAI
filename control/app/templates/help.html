Getting started

  1. Overview → Sign in now (terminal “Claude login”, claude auth login): open the link, sign in with your claude.ai account, paste the code into the terminal.
  2. Terminal → Claude · RC (remote control): confirm the prompts (e.g. trust the folder). The session then shows up in claude.ai/code and the Claude app.
  3. Tentacles → SSH hosts → Add host: This host fills in the machine tentaclAI runs on; with Docker host ticked the dialog also checks Docker, finds the stacks directory and adds the Docker service (access confirm).
  4. Tentacles → Services: connect APIs, MCP servers and repositories from templates, add tokens, then Test connection and Onboard with Claude.
  5. Settings: host name, domain, git name/email, remote control name and resources have defaults from init – change them here.
  6. Overview → System inventory: Claude gets to know your site and records it in local/CLAUDE.md.

Site & installation

tentaclAI is generic – everything site-specific lives in a few places:

.envpaths (TC_DIR, DOCKER_SOCKET, HOST_DOCS, CA_CERT), domain, resources, remote control, tokens – editable under Settings.
services/*.jsoneverything Claude can reach: Docker hosts, APIs, MCP servers, git repositories, databases, web sources, files, mail.
compose.override.yamlreverse proxy (nginx-proxy, Traefik …), extra mounts, labels for container managers. Template: compose.override.example.yaml.
local/CLAUDE.mdrules and knowledge about your site for Claude; loaded together with the generic rules on every start. The host docs (HOST_DOCS) are only referenced – Claude reads them before it works on the host.

Install on a new host

git clone … tentaclai && cd tentaclai
./tentaclai.sh init                 # one question (access: LAN port / localhost / nginx-proxy / Traefik), then builds + starts everything
./tentaclai.sh init --advanced      # every question: paths, domain, git, remote control, limits
./tentaclai.sh init --defaults      # no questions

Without a reverse proxy tentacontrol listens on port 8484 in the LAN (CONTROL_BIND/CONTROL_PORT) – keep it off the internet. For a public repository, .gitignore keeps .env, compose.override.yaml, local/, services/*.json, ssh/keys, ssh/config.d, data/ and workspace/ out; the *.example files are their templates.

How it fits together

Tentacles are everything Claude can reach – services, SSH hosts and the systems that group them – set up under Tentacles, each with its own access mode. Any other network traffic goes through the egress gateway (Network).

tentaclAIContainer with Claude Code, git, Python, Node, gh, database clients and svc – no Docker CLI or socket (docker runs on the hosts over SSH). It reaches only connected services – Docker hosts, APIs, MCP servers, git repositories, databases, web sources, files, mail.
tentacontrolThis web admin. Edits .env, services/, ssh/ of the stack and builds/recreates tentaclAI.
services/*.jsonOne file per service (parts: docker, api, mcp, git, db, web, files, smtp, imap). Tokens only as ${VAR}.
.envAll values and secrets (mode 600). svc reads it fresh on every call.
/workspaceProjects, SERVICES.md (generated service catalog), repos/ (git services).
data/claudeClaude's home (/home/claude, user claude): login, settings, history.
data/homeRoot's home in the sandbox (/root): svc state – git mirrors, caches. Claude can't read it.

Everything lives under {{ site.tc_dir }} – include it in your backups (especially data/, ssh/keys, .env).

Terminal & tmux

Every Claude terminal runs in a tmux session in the container. Closing the page or losing the connection does not end Claude – opening it again re-attaches.

The status line at the bottom of every Claude session shows that it runs in the sandbox, the model and directory, how full the context window is (ctx 42 % – yellow from 60 %, red with → /compact from 80 %) and – refreshed every 5 seconds – approvals waiting in Approvals. In long sessions Claude also suggests /compact once, where a topic ends (a rule in its base instructions – switch it off in your site rules if you don't want it). It is set in ~/.claude/settings.json only if you have no status line of your own.

Ctrl+B then Dleave the session, Claude keeps running
mouse wheelscroll the history
drag, then Cmd+C / Ctrl+Shift+Ccopy – tmux selects and hands the text to the page (Safari needs the key press)
Shift + drag (Mac: Option + drag)select in the browser instead of tmux, e.g. outside tmux sessions
Ctrl+Shift+V / right clickpaste (e.g. a login code)
Ctrl+C twicequit Claude

On the host the same works with ./tentaclai.sh, in a container console (e.g. Arcane, Portainer) with cc.

Remote control

The tmux session claude-rc runs claude remote-control permanently; when it ends it restarts after a delay. Requirements: Claude signed in with a claude.ai account (an API key is not enough) and a one-time confirmation in the terminal.

Other account: Overview → Claude Code → Sign out ends the login of the sandbox (the card shows which account is signed in) and restarts remote control; then Sign in now with the other account. Running Claude sessions stop working until then.

RC_ENABLEDon/off
RC_NAMEsession name in claude.ai/code and the app
RC_WORKDIRstart directory (e.g. /workspace or a stacks directory)
RC_EXTRA_ARGSextra arguments for claude remote-control
RC_RESTART_DELAYdelay before restarting (seconds)

The values are read fresh on every start of the session: change them under Settings, then press “Restart” on the remote control card – no container recreate needed.

Services

A service is one JSON file in services/. It can have nine parts – alone or combined (db, web, files and mail have their own sections below):

dockerDocker host – reached over SSH (this host too); Claude manages its stacks with svc docker / svc compose.
apiREST API, called with svc <name> GET /path. svc injects the authentication; tokens never appear in commands. An HTTP error (4xx/5xx) exits non-zero with the body still printed – unless the call reads the status itself with -w; a path that repeats the base URL's prefix (/api/api/…) gets a hint.
mcpMCP server (http or stdio) – registered in Claude's configuration on “Sync” as svc mcp-proxy <name>, which adds the tokens and gates every tool call by its access (default read, see Approvals).
gitRepository – cloned to /workspace/repos/<name>, read only or read/write. Commits use "author": {"name": …, "email": …} of the git part, otherwise the installation's default (Settings → Git name / email).
db · web · filesDatabase (svc db), web pages as text (svc web), directories on an SSH host (svc files).
smtp · imapSend mail, read a mailbox (svc mail).
  • Test path ("test_path"): the endpoint svc test calls for the API – pick one that needs the token, so a wrong token shows up. Without it GET / is used; the service page warns and suggests the template's path (Save as test path).
  • Rename on the service page: the file, svc <name> calls in examples and notes, @name and svc … name in job tasks, and for git services the mirror and /workspace/repos/<name> move together; tokens, system and rules stay. Deleting a service a job's task names warns, and Jobs marks such a job.
  • Token variables: a second service from the same template gets its own variables (<NAME>_…) instead of sharing the first one's tokens. If services do share a variable, the Tokens & variables card says so.
  • Template addresses use the placeholder example.com – the service page reminds you as long as it is there.

Structure

{
  "name": "paperless",
  "description": "Paperless-ngx – documents",
  "api": {
    "base_url": "https://paperless.example.com/api",
    "auth": { "type": "header", "header": "Authorization", "value": "Token ${PAPERLESS_TOKEN}" },
    "insecure_tls": false,
    "docs": "https://docs.paperless-ngx.com/api/"
  },
  "mcp": { "type": "http", "url": "https://…/mcp", "headers": { "Authorization": "Bearer ${PAPERLESS_TOKEN}" } },
  "test_path": "/documents/?page_size=1",
  "examples": ["svc paperless GET /documents/?query=invoice"],
  "notes": ["Read only unless explicitly asked"]
}
  • Status: a card shows a pill only when something is off – token missing at least one ${VAR} empty (named on the card) · disabled "enabled": false (the card is dimmed). Active services need no pill.
  • Cards: one chip per part with its access (api · write), the key chip counts the variables that are set (names on hover), the description shows two lines – click it for the full text, click again to fold it. Edit with the pencil or the name; Disable/Enable, git Fetch and moving to another system are in the … menu.
  • New tokens work for svc immediately. Only settings read at container start (e.g. GIT_*, TZ, resources) need “Apply now” – the banner also appears when a newer tentaclAI image was built.
  • Running Claude sessions see new MCP servers after /mcp → reconnect or in a new session.
  • Internal https services with your own CA: set CA_CERT in the settings – the CA becomes trusted in the container. Single devices with self-signed certificates: "insecure_tls": true.
  • Self-signed certificates (routers, NAS, hypervisors): the switch Ignore TLS certificate errors on the service page sets insecure_tls for its api, web, git, db, smtp, imap and mcp parts – encrypted, but the server is not verified.

Docker hosts

Docker management is a service like any other, always over SSH – the sandbox never gets a Docker socket. Quickest: SSH hosts → Add host with Docker host ticked (finds the stacks directory itself); or the template “Docker host (SSH)”.

"docker": { "mode": "ssh", "ssh_host": "vps1", "stacks_dir": "/opt/stacks", "access": "read" }
  • ssh_host: alias from Tentacles → SSH hosts; the user there must be allowed to run docker (or sudo it – sudo prefix on the SSH host). Docker and compose run on that host, compose in the stack's directory. This host: an SSH host with hostname host.docker.internal.
  • access: read only allows read-only commands through svc (ps, logs, inspect, config …); write allows changes – Claude asks before restarts, updates and deletions.
  • Commands: svc docker (overview), svc docker <host> ps, svc compose <host> <stack> logs --tail 50.

Onboarding a service

On every service page: Test connection checks each part (API test call, MCP reachability, git ls-remote, docker version, database and web login, SMTP/IMAP login) – in the container: svc test <name>.

Onboard with Claude runs /onboard <name>: Claude tests the service, explores it read-only (docs/OpenAPI, a few queries, repository content, stacks), asks you what it is for, typical tasks and what is allowed or off limits, and writes description, rules and examples into the service file after your approval. That way the catalog says what each service is for.

Databases db

PostgreSQL and MySQL/MariaDB with a direct connection (templates “PostgreSQL database”, “MySQL / MariaDB database”). User and password come from .env; svc passes them only via environment or a 0600 file, never on the command line.

"db": {"engine": "postgres", "host": "db.lan", "port": 5432, "database": "app",
       "user": "${APP_DB_USER}", "password": "${APP_DB_PASSWORD}", "ssl": "prefer", "access": "read"}

Claude: svc db <name> "<SQL>", tables, describe <table>, --csv; shell only for write. With read the session is read-only and statements that would switch it to read-write are refused – the real protection is still a read-only database user (see the template's setup hint).

Web sources web

Websites to read from – wikis, intranet pages, documentation. Auth: none, basic, bearer, header or form (login form with cookie, optional hidden CSRF field). Only URLs on the configured host are fetched; paths can restrict it further.

"web": {"base_url": "https://wiki.lan", "auth": {"type": "form", "login_url": "/login",
        "fields": {"username": "${WIKI_USER}", "password": "${WIKI_PASSWORD}"}, "csrf_field": "_token"},
        "paths": ["/wiki/"]}

Claude: svc web <name> <path> returns the page as readable text with links, --links lists the links, --raw the HTML, --login logs in again. Read-only; the text comes between WEB PAGE CONTENT – untrusted markers, elements hidden from a reader (display:none, hidden, aria-hidden …) are left out and counted, and the page is checked for injection attempts – see Prompt-injection safeguards.

Mail smtp / imap

Sending (smtp) and reading a mailbox (imap) – one part or both in one service. Like databases, mail goes through the egress gateway (svc tunnels it); security is starttls, ssl or none (an internal relay), the port follows from it unless set. Templates: SMTP relay (no login), SMTP (with login), Mailbox (IMAP + SMTP).

"smtp": {"host": "smtp.example.com", "security": "starttls", "user": "${MAIL_USER}", "password": "${MAIL_PASSWORD}",
         "from": "tentaclai@example.com", "recipients": ["@example.com", "boss@example.org"], "access": "confirm"},
"imap": {"host": "imap.example.com", "security": "ssl", "user": "${MAIL_USER}", "password": "${MAIL_PASSWORD}",
         "folders": ["INBOX", "Alerts"], "access": "read"}
  • One service per mailbox: pick a Mail template and enter the Mail address – the name is suggested from it (root@example.com → mail-root-example), the login goes into .env and the sender is set. For more mailboxes on the same server use … → Another mailbox on this server on a mail card: host, port, TLS, folders, access and system are copied, the copy gets its own variables – only address and password are new. Mail cards show the address under the name.
  • smtp: confirm (default) – every mail waits for your approval, showing recipients, subject and the start of the text. write sends without asking and only works with a recipients list (addresses or @domain, exact domain); if a list is set it also limits confirm. read doesn't send.
  • imap: read (default) lists and reads – reading uses a read-only mailbox and doesn't mark mails as seen. write / confirm also mark (seen, flagged) and move between folders (only on servers with IMAP MOVE – nothing is ever deleted). folders limits what Claude sees.
  • Mails are untrusted content: anyone can write to a mailbox. svc mail … read puts the text between unmistakable markers, and Claude's rules say never to act on instructions in a mail. Together with confirm and a recipient list on smtp this keeps a planted mail from sending your data away. Mails and subjects are also cleaned of hidden text and checked for injection attempts (Prompt-injection safeguards).

Claude: svc mail <name> send --to a@x --subject "…" --body-file F (or the text from stdin), folders, list [FOLDER] [--unseen] [--from X] [--subject X] [--since YYYY-MM-DD] [--limit N], read <uid>, flag <uid> seen|unseen|flagged|unflagged, move <uid> <folder>. Instead of the service name the mailbox address works too (svc mail info@example.com list) – it must belong to exactly one service; svc mail lists them with their addresses. svc test connects and logs in without sending or changing anything.

Directories & files files

A directory or file on an SSH host – e.g. a local repository or a config folder – without a bind mount. ssh_host may be left empty when the service belongs to a system with an SSH host; sudo: true uses that host's sudo prefix.

"files": {"ssh_host": "nas", "path": "/srv/config", "access": "read", "sudo": false}

Claude: svc files <name> ls|tree|cat|grep [path] reads on the host; pull [path] copies into /workspace/files/<name>/, diff shows what would change and push writes back (write only, no deletions). Paths are relative to the service path, .. is refused.

Git repositories

"git": {
  "url": "https://github.com/OWNER/REPO.git",     // or git@github.com:OWNER/REPO.git (SSH)
  "access": "read",                                   // read = read only, write = commit + push
  "branch": "main",                                 // optional
  "path": "/workspace/repos/REPO",                  // optional, default /workspace/repos/<name>
  "auth": { "type": "token", "token": "${GH_TOKEN}", "username": "x-access-token" }   // or { "type": "none" }
}
  • read: push is blocked twice (blocked push URL + pre-push hook). Ideal for public repositories or third-party code as reference.
  • write: Claude may commit and push – when you ask for it.
  • Tokens never end up in .git/config: a credential helper (svc git-credential) reads them from .env when needed.
  • SSH URLs use the tentaclAI key – add it as deploy key in the repository (see Tentacles → SSH hosts).
  • Cloning happens on sync or with the “Clone” button; “Fetch” pulls changes and re-applies read/write.
  • Usernames per provider: GitHub x-access-token, GitLab oauth2, Gitea/Forgejo any.

System inventory

This is how Claude gets to know a new site. Start: Overview → System inventory, terminal tab “System inventory” or ./tentaclai.sh inventory.

  1. tc-scan collects read-only for every docker host (over SSH): system (OS, Docker, resources), all stacks and containers (images, status, ports, proxy hosts, mounts), networks, connected services with a test call, git repositories and the SSH hosts. Environment variables and .env contents are never read.
  2. Claude summarizes and asks short rounds of questions: purpose and criticality of the stacks, taboos, container manager, proxy/DNS, backups, access, conventions.
  3. Claude shows a draft for local/CLAUDE.md and writes it only after your approval (with a backup copy).

Report only: ./tentaclai.sh scan or tc-scan in the container. The inventory can be repeated at any time – existing knowledge is kept.

Systems

A system groups the services that belong to one host or appliance – e.g. the SSH access, the docker host and the API of the same server. It has a description, an optional SSH host and rules that apply to every member. Services join with "system": "<name>" in their JSON (set it on the system's page under Services); services without a system stand alone.

  • Files: systems/<name>.json (example: systems/_example.json).
  • Docker services of mode ssh without their own ssh_host use the system's SSH host.
  • claude.ai connectors (Google Drive, Claude Docs …) come with your Claude account and reach the outside directly, not through svc. They appear as built-in tentacles at the end of the Services page and are off by default; switched-off connectors are denied in the sandbox's managed settings (root-owned).
  • A service is only needed for credentials or write access – public, read-only sources (docs, registries, public repos, websites) just need an entry under Network → Allowlist; Claude uses them directly.
  • Rule of thumb: one service = one way in with one set of credentials (an API and its MCP server may share a file); one system = one machine or appliance.
  • Claude sees systems in the service catalog and via svc systems [name]; svc info <service> also prints the system's rules.

Approvals

Parts with an access field (api, docker, git, db, files, smtp, imap) have three modes:

  • read – writes are refused (and logged as blocked).
  • write – writes run and are logged (auto). Default for api.
  • confirm – every write waits for you: Approvals shows the request with a badge in the sidebar, Approve runs it, Deny or no answer within 10 minutes stops it. A reason typed next to Deny reaches Claude and the audit log – a lasting rule (“only at night”) Claude proposes as a note. A configuration change (svc config put) shows its diff; ⚠ marks added text that reads like an instruction to an AI – check where it came from. Approve + 15 min also lets further writes of the same service part (or SSH host) run for 15 minutes without asking – listed under Active grants, revocable any time, kept across a restart of tentacontrol (like pending requests – a waiting svc call keeps waiting); never for svc config put. Claude is told to report a pending approval and never to work around a denial.
  • Not missing a request: tentacontrol shows the number of waiting approvals in the tab title and on its icon. Desktop notifications on Approvals turns on notifications from this browser – they come while tentacontrol is open in any tab, also in the background (e.g. while you work with Claude on claude.ai), and a click opens the request. A Claude session waits APPROVAL_HANDOFF seconds (Settings → Approvals, default 30, 0 = off); then svc hands the request back, Claude posts its link (/approvals#a-<id>) in the chat and runs the same command again, which waits for the same request – a decision is used only once. A running command shows nothing in the chat, so without this you would only see the request in tentacontrol.
  • The old names ro and rw still work as read and write – tentacontrol rewrites them in service files and SSH hosts on start (backup *.bak-<date>-access) and only writes the new ones. An unknown value counts as read.
  • Every approval and audit entry shows where it came from – the Claude session (Remote Control, a terminal, onboarding …) and its title, or Job · name for a scheduled job (recognised by svc, not reported by Claude). Pending approvals also show as a banner on every page. Claude's own environment reports it, so take it as a hint, not as proof.

Writes are: API calls other than GET/HEAD/OPTIONS, docker/compose commands that change something, SQL that is not a plain query (and the SQL shell), svc files … push, sending mail and marking or moving mails, git push (via a pre-push hook in every repo) and MCP tool calls the server doesn't mark read-only. What was approved, denied, run or blocked is in Logs → Audit.

Also gated: svc ssh <host> … (per SSH host, default confirm; plain status commands run without approval, even on read hosts: uptime, df, free, ps, ls, docker ps|logs|inspect …, systemctl status|list-units …, journalctl, ip a|route, ss and similar – no shell syntax, no file contents, optionally behind the host's sudo prefix) and svc config put … – Claude's way to write a service file or local/CLAUDE.md, which always needs your approval.

Claude runs as the unprivileged user claude and can't read .env, the SSH key or the audit log, nor change service files – svc (root, via sudo) is its only way out. Every MCP server runs behind svc mcp-proxy: a tool the server marks read-only (readOnlyHint) runs freely, every other one is a write – hidden and blocked on read, logged on write, asked on confirm; one marked destructiveHint counts as risky (asked on its own, even during a grant). Correct wrong marks with "read_tools" / "write_tools" (names or patterns like "get_*") in the mcp part; the service page lists the tools with their kind. Results are still checked by the injection hook.

Recent requests below the pending ones: the latest 30 decided requests of the last 30 days from the audit log – target, action, source, outcome (approved, denied, expired, blocked, or failed when the approved write itself failed) with how long it holds below (+ 10 min, grant until 14:20, always allowed, on the blocklist, no decision in time), and the approver – your username (entries from before accounts: –). All in Logs → Audit opens the same as a search (mode:confirm).

Logs: audit log & containers

Logs → Audit is one log of everything that happens, written by svc, the Claude Code hook and tentacontrol in one format:

  • tool – every tool call of Claude (Bash command, file read or edited, URL, search, MCP tool …), through the hook in the root-owned managed settings. svc commands log themselves.
  • service – every svc command on a tentacle: reads as read, writes as auto / approved / denied / expired / blocked (with who approved it or why it was blocked), each with its result and time – for a failed write also its last two error lines (secrets blanked). flagged: content that looked like a prompt injection, with the reasons under Indicators – see Prompt-injection safeguards.
  • network – the sandbox's connections through the gateway: allowed ones once per destination and 15 minutes with a count, refused ones within 30 s, your decisions on unknown destinations. The built-in destinations (Claude's API, package mirrors) only show on the Network page.
  • admin – your changes in tentacontrol (which page and object, never what you typed), terminal sessions and audit exports; auth – sign-ins, failed attempts, sign-outs, with the address.
  • job – start and end of every scheduled job run; what the job's Claude does is logged with the origin Job · name.
  • system – tentacontrol's start and what it or the entrypoint run through svc (sync, tests).

Reading it works like other log tools: one search line, the time range next to it (15 min … 30 days, all, or custom from / to), the active filters as chips below (✕ removes one), a histogram of the events stacked by outcome (click a bar or drag across bars to zoom in), and on the left the filters: for each field the values that occur in the time range with their number – tick to filter (several in one field = or, different fields = and), only to keep just that value, ⊘ to exclude it; the numbers of a field count as if it weren't filtered, so the other values stay visible. The table has one value per column – Time · Actor · Type · Target · Action · Outcome – click a value to filter by it, click a row for every field (source with a link to the session or job run, user, part · mode, exit, seconds, detail, error, address, id, severity, the indicators of a flagged entry and the raw JSON).

Search syntax: words (all must occur), field:value, -field:value (not), field:"with spaces", * as wildcard (target:mail*). Fields: actor (claude, user, job, system), user, source, type (svc, tool, network, admin, sign-in, job, system), target, action, outcome (the decision as stored – ok, read, auto, allowed, approved, flagged, denied, blocked, expired – or failed: an error or a non-zero exit; green, amber and red group them, the same words as in tentaclAI Enterprise), approver (who approved or denied a request) and grant (10 min, 15 min, until 14:20, always, blocklist), also decision (the stored decision, also for a failed call), mode, ip and cid – the correlation id: every entry of one svc call shares one (also shown on its approval card as call …), and so does every entry of one request in tentacontrol. The search, the time range and the filters are part of the address – a view can be bookmarked; Export gives exactly what matches, as CSV (the columns of the page) or JSON lines (as stored). A field: that isn't one (status:denied) is searched as text, with a hint naming the fields. In the sandbox: svc audit [n] [--since 24h] [search] with the same syntax.

Storage: data/control/audit.jsonl, at 10 MB moved to data/control/audit/<time>.jsonl; archives are removed after AUDIT_RETENTION_DAYS (Settings → General, default 90). One JSON object per line with stable, flat fields – ts (RFC 3339), id, severity (RFC 5424: 3 error, 4 warning, 5 notice, 6 info), category, actor, service, part, mode, action, decision, exit, seconds, count, detail, error, ip, origin_*, excerpts – ready for a SIEM. Secrets are never logged: API requests show method and path, bodies only as “(with body)”. Claude reads it only through svc audit and can't change it; the hook could add entries, but never remove one.

Logs → Containers shows the output of tentaclAI's three containers – tentaclai (sandbox), tentaclai-egress (gateway) and tentacontrol – live, with a line filter and a download of the last 5000 lines.

Network

All traffic of the sandbox leaves through the egress gateway; Network shows and controls it.

Mode

How the gateway treats a destination that no rule covers. learn (new installations): permissive for an hour (EGRESS_LEARN_MINUTES) from the sandbox's first connection, then enforce – the Network page then offers the destinations seen meanwhile without a rule (Allow all, or one by one). permissive (default when EGRESS_MODE is not set): allowed and recorded. enforce: held for up to 60 s while you decide in Approvals (Allow 10 min, Allow 1 h, Always, Deny, Block); refused if nobody answers. The card names the process that opened the connection (e.g. .venv/bin/python worker.py (claude)) and the Claude session or job it belongs to – looked up in the sandbox while the gateway holds the connection, a hint like every origin – and how many connections wait for the same decision; Logs → Audit keeps both with the time of the first request (requested). Recent requests on Approvals notes Always and Block under Decided by – they last, unlike a plain Allow or Deny. EGRESS_MODE in .env.

IP targets

Connections to a bare IP address instead of a name (curl https://93.184.215.14). Normal programs almost always use names, so in enforce mode such a connection without a rule is blocked (block, default) or asked about like any other unknown destination (ask). In permissive mode it is allowed like everything else. EGRESS_DIRECT_IP in .env.

Rules

Checked in this order: Built-in (Anthropic, GitHub, PyPI, npm – always allowed, can't be blocked) → Blocklist (always refused, even for tentacles) → your allowlist (added here, with Allow on a seen destination, or Always in Approvals) → tentacles (hosts of your active services and SSH hosts, derived live) → temporary approvals. Entries: host, *.domain (subdomains only), an IP or a range like 10.0.0.0/8, each optionally with :port. The gateway resolves names itself and checks IP rules against the resolved address, so a blocked range can't be reached through an allowed name. Seen lists every destination with its rule and last result – newest first; click a column header to sort by it (again to reverse), the choice is remembered in this browser.

Jobs

Jobs run Claude tasks on a schedule – reports and checks such as patch status, certificate expiry, disk space or last night's backups (templates for these are offered). The switch on a job pauses it (the card dims and says paused – no automatic runs; Run now still works). The copy icon (Clone) copies a job (the copy starts paused). Groups sort jobs by topic (e.g. Spam handling, Project XY) – one group per job: set it in the editor (click an existing group or type a new name) or pick it in the small menu on the job's card (New group… names a new one, No group takes it out). As soon as one job has a group, the Jobs page shows one tab per group (plus All and No group) with the number of jobs and a red or yellow count of jobs whose last run ended in alert or warn; the page remembers the tab you picked. svc jobs --group <group> lists one group. A job is a task, a schedule (every hour, daily or weekly at a time, every N hours, a cron expression, or manual – then it runs just with Run now), a profile and a notification rule. Each run is a fresh Claude session with a 20-minute limit (adjustable); only one run at a time, a run that is still going skips its next turn, a run missed while tentaclAI was down is made up for if it is at most 6 hours old, and runs are skipped while a plan limit is at 90 % or more. Claude answers with a traffic light – ok, warn or alert – plus a title and a summary; by default you only hear about warn, alert and failures, and the badge next to Jobs in the sidebar counts the ones you haven't looked at – the Jobs page lists them on top under New since your last visit (also runs further down the history, opened and marked new; Mark all seen clears the list) (events Job finding and Job failed in Notifications).

Naming tentacles: write @name in the task (the editor completes service and SSH host names). Saving checks that they exist and warns when something won't work – a disabled service, sending mail from a read-only job, a confirm tentacle whose approval nobody gives at night. Claude gets a line about each named tentacle, so it doesn't search the catalog first. A tentacle the task calls with svc (svc mail box list, svc ssh nas uptime, svc api GET /) counts as named too. With Only the tentacles named in the task the run may use nothing else (the editor lists what the saved task allows): svc refuses every other service and SSH host, MCP servers only those of the named services (each through svc, claude.ai connectors are off) – least privilege for a job that, say, reads mail. While a run is going its row shows a spinner, the running time and Claude's steps live – each tool call (e.g. the svc command), its output and Claude's text; the page reloads by itself when it ends. Finished runs keep their steps under Claude's steps – the quickest way to see why a job reported warn.

Proposing instead of acting: with Propose actions (read-only profile) the run only analyses and returns proposed changes – each a title and exactly one svc command (at most 500 characters on one line, no pipes, ;, $, backticks or backslashes, no svc config; others are shown as refused, with the reason under output). The run lists them right below its row with check boxes for 24 hours, and the badge next to Jobs counts them (pulsing, like approvals); Discard selected / Discard all drop proposals you don't want; Run selected runs exactly the picked commands through svc, without Claude – read stays read, a confirm tentacle asks for approval as usual (the banner shows it right away), and a job limited to its named tentacles stays limited. Example: a spam check proposes svc mail box move 912 Junk at night, you pick it in the morning – no approvals at 3 a.m.

Learning from runs: every run may return what it learned – a note to add, fix or drop for a service, a system or the site rules – and, with Suggest prompt improvements (on by default), a better version of its own task when the task was unclear – a minimal change without details of that run, shown as a diff against the task the run had, with the word count before → after. Both show under the run: you pick which notes go in (Apply selected, with a backup; a note that changed since the run is left alone, ⚠ marks text that reads like an instruction to an AI) – a weakness of tentaclAI itself (a missing svc option, a misleading message) is listed apart under For tentaclAI, never written into your notes, with Report on GitHub (a prefilled issue you check before sending) – and take a better task with Use this task – the editor keeps the last 5 versions under Earlier versions. A new installation comes with two built-in jobs that use this, paused (every run uses your Claude plan) – edit them freely or pause them (they can't be deleted), Reset to default in the editor; while you don't change a built-in task, it follows improvements in later releases. An existing installation gets them as templates under Add job: Learning review (weekly – the audit log of the last 7 days: repeated failures, repeated exploration, reasons of denials) and Knowledge cleanup (monthly – merges, cuts and moves notes, the site rules and Claude's memory to stay within the budget: KNOWLEDGE_LOCAL_KB, default 6 KB of site rules read in every request, and KNOWLEDGE_NOTES, default 8 notes per service or system; Claude → Instructions shows where you stand).

From the terminal: svc jobs lists the jobs, svc jobs <name> [--runs N] [--steps] shows a definition (as JSON) with its recent runs and, with --steps, Claude's steps – so you can ask Claude why a job reported warn and have it tune the prompt. svc config put job <name> <file> creates or changes a job: tentacontrol checks it with the editor's rules first, then it waits for your approval in Approvals (preview: schedule, profile, start of the task); a new job starts paused – switching it on stays here. A running job can't create or change jobs.

{"name": "Mail test", "prompt": "Send a test mail via @mailrelay …", "schedule": {"kind": "daily", "time": "07:00"},
 "profile": "standard", "scope": true, "improve": true, "notify": "findings", "model": "haiku", "max_minutes": 5}

The profile is the job's limit on top of each tentacle's own access – the stricter one wins. The job list shows it the way the service cards show access: reads (neutral), writes (purple – hover it to see which tentacles it writes to without asking and which ones ask first) and proposes; yellow is kept for things that wait for you. read-only (default): every tentacle counts as read, files in the sandbox can't be edited, MCP servers offer only the tools they mark read-only (through svc; claude.ai connectors are off). Two layers enforce it: Claude Code only allows reading tools, svc and a few text tools for pipes (svc … | grep … | head – Settings → Jobs, default echo, head, tail, grep, jq, sort, uniq, wc, cut, tr, date, sleep; shells, interpreters, awk/sed/find/xargs and network or write tools are refused), and svc itself recognises the run (by a marker on the run's wrapper process and root's list of running jobs) and refuses every write – a marker Claude makes up can only make it stricter. standard: like a terminal session – confirm tentacles wait for your approval in Approvals (shown as “Job · name”; it expires after 10 minutes and the job reports that), write tentacles are written without asking; the editor lists them.

SSH targets

tentaclAI has its own key (ssh/keys/tentaclai_ed25519). Each host is a Host block in ssh/config.d/. Everything works in the UI:

  1. Add host – alias, host, user, port, optionally a jump host (ProxyJump through another SSH host) and sudo.
  2. Confirm the host key – tentaclAI fetches it and shows the fingerprint; compare it with ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub on the host.
  3. Authorize tentaclAI – enter the user's password once (passed to sshpass via stdin, never stored or logged), or add the key by hand with the shown command.
  4. The host is saved and tested (login, sudo).

Edit changes host, user, port, jump host, sudo and the alias – a rename also updates docker/files services, systems, other hosts that jump through it and job tasks that name it. If a host key changed, Check host key fetches and confirms the new one. Remove can also take tentaclAI's key off the host. On the command line: ./ssh-host.sh list|add|sudo|hostkey|remove|test – same logic as this page.

Hosts without root login: sudo

If the SSH user is not root, enable use sudo (when adding the host, or later in the sudo column). The prefix (default sudo -n, also e.g. doas) is stored as # tentaclai: sudo=… in the host's block. svc docker/svc compose and tc-scan use it automatically, and Claude's instructions list it per host for admin commands.

It is non-interactive: the user needs passwordless sudo, ideally limited, e.g. /etc/sudoers.d/tentaclai: deploy ALL=(root) NOPASSWD: /usr/bin/docker. “Test” checks login and sudo.

Claude

Everything that steers Claude in the sandbox, in one place. Changes apply to new Claude sessions.

Instructions

Instructions shows how Claude's instructions are put together: in every session Claude reads ~/.claude/CLAUDE.md, generated at every start and sync from the base rules (image), the host tables (from your tentacles) and an import of your site rules (local/CLAUDE.md). When needed it looks up the rules of a service or system (notes, shown by svc info / svc systems), the service catalog /workspace/SERVICES.md and – for work on the host – the host documentation (HOST_DOCS). The site rules are edited right there (the previous version is kept as .bak-…); /inventory drafts them, and Claude can propose changes with svc config put local (always waits for your approval). The generated CLAUDE.md can be viewed, not edited. Learning: what Claude finds out while working, or what you tell it (also as the reason of a denial), it records on its own where it applies – a service's notes (svc config put service), a system's notes (put system) or the site rules (put local) – every change through Approvals with its diff; facts about the environment go there, not into Claude's own memory. Service and system rules are edited on their own pages.

Memory

Memory lists what Claude noted for itself (~/.claude/projects/*/memory/): MEMORY.md is the index read in every session, the entries are opened when they matter. Deleting an entry also removes its line from the index.

Models

Models: Models sets the model and effort for every session (terminal and Remote Control), for subagents and for the set-up commands /inventory and /onboard – e.g. Sonnet for routine work saves plan quota. Standard leaves the choice to Claude Code. A fresh installation runs subagents and the set-up commands on Sonnet. Written as model, effortLevel and CLAUDE_CODE_SUBAGENT_MODEL into Claude's settings.json and into the commands' frontmatter; a /model switch inside a session only lasts for that session.

Skills

Skills of Claude Code and your account: Skills sets each one to On, /command only (only when you call /name) or Off – every skill Claude is offered costs context in every request. Those that make no sense in a headless sandbox (Office files, Artifacts, browser and computer use …) start off. Written as skillOverrides into Claude's settings.json; entries of your own for other skills stay. inventory and onboard are required by tentaclAI (its buttons start them) and can't be switched off – /command only keeps them working.

Site skills are procedures of this installation (renew a certificate, onboard a host …): when one comes up again, Claude offers to keep it and proposes it with svc config put skill <name> <file> – a SKILL.md with name and description (when to use it) in its frontmatter, then the steps. After your approval (with the diff) it is stored as local/skills/<name>/SKILL.md and svc sync copies it into Claude's skills, for every session and job; a skill Claude made itself under the same name is left alone. They are listed here as site skill with their steps and a mode like the others; Remove keeps the file as .bak-… and takes it away from Claude.

Usage

Usage shows the plan limits (session and week, account-wide) and what contributes to them – from Claude Code's /usage, asked every 10 minutes without a model call – plus tokens per day, the sandbox's sessions and the models used, read from the local session files (usage fields only, never the conversation). A quota notification goes out at 80 % and at 100 %, once per limit window – a restart of tentacontrol does not send it again.

settings.json

settings.json edits Claude Code's own settings in the sandbox – for everything without a page of its own (permissions, language, attribution, cleanupPeriodDays …; see the Claude Code settings). The parts other pages manage (skillOverrides, model, effortLevel, the subagent model and the telemetry switches) are left out and stay as they are; env values with secret-looking names are masked. The JSON is checked before it is written, the last 5 versions are kept as settings.json.bak-…. The managed settings (blocked connectors) are a policy Claude can't change and are not editable here.

Settings

Edits the stack's .env. Secrets are never shown – variables whose name looks like one (TOKEN, KEY, PASS, SECRET, AUTH, PAT …) and every variable a service uses as a credential (in auth, headers, password …) – leaving the field empty keeps the value, the “clear” checkbox removes it. Changes that need a new container show “Apply now” at the top (running sessions end); remote control changes only need “Restart” on the overview.

Notifications

Settings → Notifications: add channels (ntfy, webhook, e-mail – server, port, security, sender, recipients, optional login – or any Apprise URL – Telegram, Discord, Slack, Teams, e-mail, Home Assistant), send a test, and tick which event goes to which channel. Possible prompt injection goes where approvals go until you set it. Urgent events (approval needed, Remote Control down, signed out, container stopped) also come during quiet hours; the same event is sent at most once per dedupe interval. Channel URLs are stored in .env as NOTIFY_URL_….

Account

Settings → Account: the username you sign in with (it names you in the audit log and on approvals), your email and an optional name – saving needs the current password; there you also change the password (that revokes the browsers trusted for two-factor sign-in). The account is created at the first setup; an installation from before accounts asks for username and email once after the next sign-in.

Settings → Account also switches on two-factor sign-in: scan the QR code with an authenticator app (Google Authenticator, Aegis, 1Password, Bitwarden …), enter its code, keep the 10 recovery codes (each works once, for a lost phone). From then on tentacontrol asks for a code after the password; “Trust this browser” skips it for 30 days in that browser – the trusted browsers are listed there and can be revoked. Switching off needs the password and a code. No phone and no recovery code: ./tentaclai.sh reset-2fa on the host. A sign-in with a recovery code sends a notification.

Export / Import

Settings → Export / Import saves the configuration as one JSON file – services, systems, SSH hosts, jobs, network rules, notifications (channels without their URLs, routes, quiet hours), the site rules local/CLAUDE.md, the site skills (local/skills; on import, like the site rules, only picked on request – read their steps first) and the plain settings (without host paths) – to keep it or to set up a second installation. No secrets: tokens, passwords, channel URLs and SSH keys stay in .env and ssh/keys; the file lists only the names of the variables the configuration needs. A plain value in a service's credential field (instead of a ${VAR}) is left out and shown on the page. The file still holds host names and addresses – don't share it publicly.

Import is two steps: the uploaded file is compared with this installation (new, changed with a diff, same, invalid with the reason) and nothing changes until you pick entries and click Import picked. Every entry goes through the same checks as the editor; SSH hosts come over only as host, user, port, jump host, host key alias, sudo and access – no other ssh options. An overwritten file keeps a copy *.bak-<date>-import; new jobs start paused, new notification channels disabled; network entries are added to the lists, not replacing them. Site rules and settings are not picked by default. Afterwards the variables still empty can be filled in right there; imported SSH hosts need this installation's public key.

Templates: “Template” on a service page downloads the service as a template – name, system and TLS exception left out, its own variables as EXAMPLE_…, svc <name> as svc NAME, the internal domain (TC_DOMAIN) as {{ '{{DOMAIN}}' }}; fixed addresses that remain are pointed out. Services → Import a template … saves one in local/templates/ (marked own in the list); names of built-in templates and plain values in credential fields are refused.

Modules

Modules extend tentacontrol with pages, sidebar entries, tabs, background tasks, notification events and parts of Export / Import. Modules lists them by origin:

  • Built-in – shipped with tentaclAI, off until you enable them: Service-Health tests every service on a schedule and notifies on outages (its own section below, once enabled).
  • Third-party – your own or someone else's, in local/extensions/<name>/ of the stack directory (a Python package with an extension.json). Off until you enable them – a module runs inside tentacontrol with all of its rights (it can read the configuration, approve requests and run svc), so only enable code you trust. Its pages live below /x/<name>/; it can't replace tentacontrol's own pages.
  • Enterprise – packages named in TC_EXTENSIONS (none by default): always loaded, they may provide a license that unlocks modules.
  • Signed by tentaclAI – a module package installed with Install from file and signed by tentaclAI (e.g. handed out as a file or by tentaclAI Enterprise): always loaded, the same rights as Enterprise.

Add module (Install from file) takes a module package (.tcpkg.zip) – no internet needed. tentacontrol checks it first and shows name, version and whether tentaclAI signed it; nothing is installed before you confirm. An unsigned package is a third-party module and needs I trust this code. Every file is checked again at each start: a package changed after installing is not loaded. An update keeps the version before it (Roll back); Remove deletes the files, data the module stored stays. Packages are not part of Export / Import – install them again after a restore.

Enable takes effect when tentacontrol restarts (Restart tentacontrol – a few seconds, the sandbox and Claude keep running); Disable at once. Loading, enabling and disabling land in the audit log. Until it is enabled, tentacontrol reads only a module's extension.json – its code is never run. Writing a module: docs/extensions.md in the repository, with the example examples/extensions/tcx_hello.

Central management

Enterprise (sidebar) connects this installation to a central server (tentaclAI Enterprise) as an agent: paste the server's enrollment code and pick the parts of the configuration it may manage. The connection always goes from here to the server (every 30 s); nothing has to reach this installation.

  • The server sees this installation (version, modules, services – never credentials) and receives the audit log. Entries not sent yet are kept, also past the retention, until the server has them.
  • A profile from the server sets items of the allowed parts: enforced ones are locked here (marked central, refused in tentacontrol and in svc config put, and reverted if a file is changed on the host), defaults may be changed here. Credentials stay in this installation's .env – values the profile needs and that are empty here are listed on the Central page.
  • Profiles are signed by the server; without the server the last one stays in force. Every change the server makes lands in the audit log.
  • Leave ends it: the values stay, nothing is locked any more. Management is governance, not a sandbox – root on the host can always change files; the server sees the difference.

The server can also hide parts of tentacontrol (Terminal, Jobs, Network, Modules, Claude, Export / Import, Updates – if you allow Features) and show a message at the top of every page; × closes it until the next sign-in. What the server may manage can be changed later on the Enterprise page – unless the server's profile turns on tamper protection: then leaving is off and parts can only be added; attempts are refused and reported to the server (only revoking there ends it). The profile can also lock the choice, or set it to all parts.

Sign-in through the server (if you allow Sign-in and CONTROL_URL is set): users of the server sign in here with Sign in with … – no local account; the server checks their password, second factor and whether they are granted this installation. A profile can allow only these sign-ins. Emergency access for the local admin then: ./tentaclai.sh passwd (or passwd --open, keeping the password) on the host opens the local sign-in for an hour.

Protocol: docs/central.md in the repository.

Community & Enterprise

This is tentaclAI Community, the free, open-source edition – complete on its own, no license needed. tentaclAI Enterprise is the central management for many installations: a server of its own that installations join under Enterprise in the sidebar (with a lock until then; afterwards a dot shows the connection). It holds the audit log of every installation, hands out configuration with profiles, runs jobs on all of them and distributes signed modules; compliance reports and a SIEM export are planned there. Enterprise is licensed on its server (seats = installations), not here.

Settings → License shows this installation's Installation ID (TCI-…) – it identifies the installation, e.g. on the central server. It is derived from the machine's hardware (a hash of the system UUID its firmware reports, or of the Docker engine's ID where there is none), worked out on every start and never stored, so it can't be set by hand or copied along with the data.

Updates

tentaclAI releases: tentacontrol checks the GitHub releases every 6 hours (no token, nothing is sent except the request itself) and shows “Update available” in the sidebar; the Updates page lists the upgrade steps of the release. Update with ./tentaclai.sh update on the host – it shows the changes and upgrade steps, pulls, rebuilds and asks before recreating each container. Turn the check off with UPDATE_CHECK=false, point it to a fork with UPDATE_REPO (Settings → Updates).

Claude Code is installed when the image is built. “Update now” rebuilds the image (with a fresh base image) and recreates the container. Pin a version with CLAUDE_CODE_VERSION in the settings. tentacontrol itself is updated on the host: docker compose up -d --build control.

Security

  • tentacontrol has the Docker socket of this host (to run tentaclAI) – that is root on {{ site.hostname }}. Choose the tentacontrol password accordingly.
  • In tentaclAI, Claude runs as the unprivileged user claude. .env, the SSH key, the service files and the audit log belong to root; svc (via sudo) is the only way to services and enforces read/write/confirm. Client tools run as a third user (tcrun) with only their own secret.
  • Network: permissive records every destination, enforce asks for unknown ones – see Network.
  • tentacontrol is out of Claude's reach: from the sandbox only svc's endpoints for approvals and job proposals answer (with its token; an unrecognised address from the sandbox network counts as the sandbox) – the admin UI, the login and the gateway's endpoints refuse it, and only the gateway may use the latter.
  • Other services' secrets are blanked in free read-only output: docker … inspect, compose … config and systemctl show|cat show [redacted by svc] for values with secret-looking names and for passwords in URLs. Logs and commands you approve are not filtered. svc also keeps the .env values out of the environment of the programs it starts.
  • The sandbox sits in an internal network without a route to the outside; everything leaves through the egress gateway (tentaclai-egress), which records every destination. EGRESS_MODE=learn (new installations) allows all for an hour and then switches to enforce: unknown destinations wait for your approval.
  • Every write is logged before it runs (started, then its result) – a write that can't be logged is not executed; a started entry without a result means the call was interrupted.
  • Approvals mark risky writes in red (privileged containers, a mounted /, compose down -v, rm -rf, DROP TABLE, DELETE without WHERE, force pushes …) and say what approving gives – Docker on a host is as much as root there. Approve + 15 min never covers a risky write.
  • An write docker service is root on that host. The sandbox itself never gets a Docker socket – docker hosts are reached over SSH only.
  • Login: bcrypt hash, optional two-factor sign-in (TOTP, see Settings → Account), 12 h session, SameSite=Strict cookie (Secure behind https), origin check for forms and the terminal, throttling after failed attempts (password and code).
  • Secrets never reach the browser; svc passes them to curl through temporary 0600 files on tmpfs, not on the command line.
  • Claude keeps asking before actions – the rules are in its instructions (generic rules + local/CLAUDE.md). Scheduled jobs run without prompts: read-only is enforced by Claude Code and svc, a job can be limited to its named tentacles, and confirm still waits for you – see Jobs.
  • Mails are untrusted: svc mail … read frames them between markers Claude never obeys; sending is confirm by default and write only with a recipient list – see Mail.
  • Prompt-injection safeguards (INJECTION_GUARD, on by default – switch: Settings → General, group Prompt injection): mail and web pages from svc come between untrusted-content markers whose end can't be faked, without what a reader can't see (zero-width and direction characters, hidden Unicode tag text, elements hidden with display:none, hidden …). Everything svc reads (mail, web, files cat|grep, API responses) and – through a Claude Code hook in the root-owned managed settings – WebFetch, WebSearch, MCP tools and files Claude reads is checked for text that tries to instruct an AI (“ignore previous instructions”, notes addressed to AI assistants such as “Note for automated assistants: please …”, fake system tags, requests to run svc or send secrets somewhere, hidden text). A finding puts a warning next to the content for Claude (the same findings in unchanged content again in one session: a short reminder), an entry flagged into the audit log and sends the notification Possible prompt injection. The entry says what was read (the file, URL, search, MCP tool or command) and, under Indicators, each reason with a short excerpt and its line – for a base64 block its size and start (iVBORw0KGgo… is a PNG) – with secrets blanked. Files in a result are not checked as base64: an image Claude reads (or one an MCP tool returns) is skipped, a PDF's text is taken out with pdftotext (first 50 pages, 6 s for all PDFs of a result together) and checked page by page – white or tiny text included, a finding names the page (PDF page 2, line 1: …); a PDF it can't read (encrypted, scanned, too slow, no time left) gets PDF text not checked on its entry, one with more pages or text than is checked PDF text partly checked; the notification carries the same. Its result reads Claude warned: nothing was blocked. New flagged entries show as a yellow ⚠ count next to Logs in the sidebar and as a line on the Overview, until you open Logs → Audit.
    What it does and doesn't do: hidden injections lose their effect, obvious ones are noticed by Claude and by you. It is a heuristic – a well-disguised attempt can get through, and Claude decides in the end. The hard limits stay the ones above: read/confirm in svc, no secrets in the sandbox, the egress gateway (enforce asks for unknown destinations) and recipient lists for mail. For tentacles that read mail or the web, keep writes on confirm.
  • Forgot the password or username: ./tentaclai.sh passwd on the host (shows the username; --username <name> sets a new one).

Roadmap

Focus: the core. Modules and the tentaclAI Enterprise integration stay as they are – they keep working and get fixes, but no new features for now. Development concentrates on the sandbox, svc, the egress gateway, the audit log and a faster first setup.

  • Short-lived SSH certificates: instead of one permanent key authorized on every host, tentaclAI runs a small SSH CA and signs a certificate per call or session, valid for minutes and limited to the host and principal it needs; hosts trust the CA once (TrustedUserCAKeys), revoking means removing the CA, and every certificate is in the audit log.
  • AI Assist for jobs: describe what a job should do and Claude drafts it in the editor – task, schedule, profile, the tentacles it names and when to warn – or improves an existing one; you check and save it.
